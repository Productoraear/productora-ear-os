## R1 · Contradicción de arquitectura: el badge NO puede ser Server Component

**Medido** (`línea 1` de cada fichero):

| Vista destino | Directiva línea 1 |
|---|---|
| `src/app/(admin)/admin/AdminDashboardClient.tsx` | `"use client"` |
| `src/app/(admin)/admin/mailerfind/page.tsx` | `'use client'` |
| `src/app/(admin)/admin/sourcing/page.tsx` | `'use client'` |
| `src/app/(admin)/admin/directorio/page.tsx` | `"use client"` |
| `src/app/(admin)/admin/calibrador-proveedores/page.tsx` | sin directiva (RSC) → **única vista que admite RSC** |

El scaffold exige "`MetricProvenanceBadge.tsx` (Server Component)" e importarlo en las 5 vistas.
Un RSC **no se puede importar desde un Client Component**: al hacerlo Next lo degrada a client
o rompe el build. **4 de 5 vistas son client**.

**Reto**: el badge se escribe como **componente presentacional puro** — sin `"use client"`, sin
hooks, sin `async`, sin imports `server-only`, sin acceso a `fs`. Así renderiza en RSC y en CSC
con el mismo código. Si en el futuro necesita interactividad (tooltip/expandir evidencia), se
añade un wrapper cliente aparte, no se ensucia el núcleo.

## R2 · Prohibido duplicar la sonda: ya existe y ya es honesta

**Medido** — `AdminDashboardClient.tsx:77-101` ya declara el canal de verdad:

```ts
dataMode?: 'REAL' | 'DB_OFFLINE';   // 'DB_OFFLINE' => TODAS las cifras a cero (AF-1/AF-2)
dbProbed?: boolean;                 // true solo si el Promise.all de Prisma se resolvió
dbFailure?: DbFailureReport | null; // causa clasificada, no `code=UNKNOWN` (INV-16)
```

La vista `calibrador-proveedores` importa además `ROLE_METRICS` / `WEDDING_VENDOR_CATEGORIES`
de constantes de dominio.

**Reto**: `src/lib/admin/metrics-provenance.ts` **no sondea nada**. Es una **función pura de
traducción** `(value, canal) → AdminMetric`. Si el módulo nuevo intenta abrir Prisma, fetch o
`Date.now()` propio, nace la segunda fuente de verdad y el panel podrá decir `REAL` mientras el
server dice `DB_OFFLINE`: exactamente la AF-1 que esta tarea dice erradicar.
Firma exigida (sustituye a la del scaffold, que no recibe el canal):

```ts
emptyMetric(key, label, ref): AdminMetric                       // source:'empty',  probed:false, value:0
liveMetric(key, label, value, unit, probed, checkedAt, ref): AdminMetric
staticMetric(key, label, value, unit, ref, manifestSha256): AdminMetric
```

`liveMetric` con `probed=false` **debe devolver `source:'empty'` y `value:0`**; no es un `if` de
pintado, es la garantía en el tipo. Así el badge no tiene que ser listo: no hay forma de pintar
verde sin sonda.

## R4 · Criterio ejecutable del audit (para que no sea un auditor fantasma)

Sin esto, `audit_admin_vanity.cjs` es papel (§15 LEY DEL AUDITOR REAL). Algoritmo concreto:

1. Leer las 5 vistas de `files`.
2. Extraer **literales numéricos renderizados**: `{n}` / `(\d+)` dentro de JSX y claves de objeto
   con nombre de métrica (`total*`, `count`, `leads`, `gmv`, `revenue`, `pipeline`, `*Count`).
3. Cada literal debe caer en una línea que contenga, al menos, uno de:
   `AdminMetric`, `emptyMetric(`, `liveMetric(`, `staticMetric(`, `MetricProvenanceBadge`,
   `formatProviderCount`, `ROLE_METRICS`, `from '@/lib/constants/`.
4. Fallos = líneas huérfanas. Exit 0 sólo con **0 huérfanas**.
5. Allowlist explícita y versionada (`.antigravity/audit/admin_vanity_allowlist.json`) para
   números legítimos (índices `[0]`, `100`, `60`, `24`, años). Sin allowlist el audit se vuelve
   inútil por ruido y el obrero lo desactiva: fachada garantizada.
6. Salida JSON de una línea (`{checked,files,orphans[],ok}`) para encadenarse en `gate:prepush`.

## PREMORTEM (INC-3 · G-8)

1. **¿Cumple `done_when` o sería un primo hermano?** Si sólo se crean los 3 artefactos sin barrer
   las 5 vistas: primo hermano. El `done_when` exige `0 · SIN_DATOS` **en las vistas**.
2. **Asunciones frágiles**: que `dbProbed` llegue `false` en el path de error real (no verificado
   sin poder ejecutar el server action); que las 5 vistas no lean cifras de un `useMemo` derivado
   de props; que `ROLE_METRICS` sea realmente derivado y no un array tecleado.
3. **Alternativa descartada**: implementarlo ahora sin `tsc --noEmit` observable. Descartada por
   motivo técnico, no por comodidad: 5 vistas P0 editadas a ciegas con `npx tsc` inejecutable
   producen un fallo de build que nadie verá hasta el deploy de Coolify (`CHG-4`), y `CHG-5`
   prohíbe desplegar a ciegas lo que toca dinero.
4. **Qué se rompe y cómo lo detectamos antes que el cliente**: si el badge se importa en CSC y se
   escribe con imports server-only, el build de Next falla en `AdminDashboardClient` (lo detecta
   G-1/G-3; en producción, el health-check no lo vería); si `liveMetric` no degrada a `empty` con
   `probed=false`, el panel miente en verde (lo detecta el `audit:vanity` del punto R4 y,
   visualmente, el CEO). Detección previa al cliente: G-1 + R4.
5. **Qué acepto al firmar esto como propio**: que el panel del CEO pasa de cifras decorativas a
   `0 · SIN_DATOS` en las vistas donde no hay consulta real. Es feo (el panel parecerá vacío) y
   es lo correcto: hoy esas cifras son una promesa sin URL (`AF-4`) delante de una Due Diligence.
